VU1 runaway: cost attribution, 2026-09-10, build-debug

Instructions counted per termination reason. An earlier version of this
census recorded only a per-program total and the cut-off cost was then
DERIVED as (budget runs x maxCycles). That is wrong: maxCycles is a
cycle budget and a stalled run burns cycles without retiring
instructions. It produced a confidently wrong '89% of VU1 time'.
The numbers below are measured, not derived.

GHPC_VU1_BUDGET=1000000, 420s run (this run did NOT reach StartGame):

  cut-off (budget) invocation 285786 instructions, 124x
  8.6% of runs consume 92% of all VU1 instructions
  pc0x30b0 cut-off runs average exactly 1000000: unbounded at any cap

GHPC_VU1_BUDGET=65536 (default), 600s run that DID reach gameplay:
[vu1/census] total=100000 pc0xcd8{ebit=65893 budget=30961 offend=0 stop=2283 avgInstr=22982 maxInstr=65536} pc0x2e60{ebit=87 budget=0 offend=0 stop=0 avgInstr=112 maxInstr=167} pc0x30b0{ebit=749 budget=27 offend=0 stop=0 avgInstr=2869 maxInstr=65536}

CONFOUND, stated rather than buried: the two runs are not the same
regime. At budget=1000000 the guest never got through the count-in in
420s, so its census describes menus and loading. Do not read the
31% -> 20% change in cut-off rate as truncation being cured; the
populations differ.

That slowdown is itself the evidence: handing the programs 15x more
rope made the guest slower and delivered no extra progress. Honest work
being truncated would complete; a runaway just runs longer.

Different runaways stall in DIFFERENT loops (0x0b10, 0x32b0, 0x0e98,
0x15c0), so this is not one mis-decoded branch. offend=0 everywhere:
the pc never leaves code memory. 0x0b10 is also where the [projw] probe
reports the projection matrix going corrupt.
